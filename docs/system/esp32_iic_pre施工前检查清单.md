# ESP32 统一测距施工前检查清单

**日期：** 2026-09-21
**状态：** E5 代码施工已完成；等待真机和 OTA 验收
**适用范围：** J100(P)-485、CYD3S1612-IIC、ESP32 固件、Demo APP、SW APP

## 1. 施工目标

同一份 ESP32 固件能够根据实际安装的传感器工作：

1. 485 或 IIC 驱动先被 ESP32 读取。
2. ESP32 将各自的原始数据转换成统一的物理距离 `distance_mm`，并同时给出数据质量。
3. ESP32 用统一距离链判断空载、有人、稳定、离开、律动、摔倒和 `start_ready`。
4. 体重是独立的测量链：有合格模型时提供体重，没有合格模型时不阻塞距离状态链。
5. Demo APP 负责校准、采样、模型写入和显示；SW APP 只消费正式状态。

## 2. 真相源和边界

| 内容 | 唯一责任方 | 施工前必须保持的边界 |
|---|---|---|
| 传感器原始帧、引脚、转换系数 | ESP32 传感器层 | 以实测协议和本地产品说明书为准，不能让 APP 猜原始值 |
| 统一距离、距离质量、后端类型 | ESP32 测量层 | 485/IIC/以后新增传感器都输出同一接口 |
| 空载/有人/稳定/离开/律动/摔倒/start_ready | ESP32 状态层 | 以统一距离及其变化为依据；BASE 原有无激光路径保持不变 |
| 体重模型和体重数值 | ESP32 + Demo APP | 0 kg 点由 APP 记录的人工输入确定；一次、二次模型都必须经过该点 |
| Demo 校准、采样、实时显示、日志 | Demo APP | 不能把“距离有效但体重无效”样本整体丢弃 |
| 正式状态给 SW APP 的映射 | ESP32 BLE 协议 | 字段和语义保持兼容；SW APP 不参与距离或体重计算 |
| OTA | ESP32 固件 | 维持现有升级和回退机制，不与传感器施工混改 |

## 5. 必须先通过的施工门槛

### A. 协议门

- 明确 `distance_valid`、`weight_valid`、后端类型和失败原因。
- 正式状态仍由 ESP32 产生；Demo 只显示和操作，SW APP 只显示状态。
- 无效距离不能进入状态判断；体重无效不能阻塞距离状态判断。

### B. 传感器门

- 记录真实 485 帧、GPIO17/18、串口参数、地址和 J100 的 100 mm 基准。
- 记录 IIC GPIO15/16、地址 0x30、启动时间、量程和异常读数。
- 分别验证：只 485、只 IIC、双设备、两者都不可用。

### C. 固件门

- 探测层必须真正区分 IIC、485、冲突和不可用，不能因 IIC 失败才偶然尝试 485。
- `MeasurementReadResult` 必须区分传输错误、数据错误、范围错误和过期数据。
- 校准模型采用带版本/完整性校验/提交标志的原子保存；重启后必须读取同一模型。
- “参数归零”只清除已保存模型和校准状态，不得把当前距离偷偷写成新的正式零点。
- 运行时零点不得自动改写正式模型；诊断零点与正式模型分离。

### D. Demo APP 门

- 参考体重输入 0 kg 后点击“记录校准点”，该点成为本次模型的必过空载点。
- 一次、二次拟合都以 `u = distance - empty_distance` 计算，截距固定为 0；仍保留两种拟合选项。
- 写入模型后必须收到 ACK，并重新读取模型确认参数、空载点和版本。
- 采样、实时显示、日志应保留距离有效但体重无效的样本，并明确标注质量。
- 空载容差由设备/传感器配置决定，初始建议 ±0.10 mm；CYD 需要按实测重复性单独配置。

### E. SW APP 门

- 只做只读回归审计：解析正式状态、按钮状态、停止/安全原因、BASE/PLUS 降级语义。
- 不增加距离、体重、拟合或传感器探测逻辑。
- 只有当 ESP32 改变正式状态字段或语义时，才重新评估 SW APP 改动范围。

### F. 验收门

- 单元/编译：固件、Demo APP 协议和拟合测试通过。
- 真机：两种传感器使用同一固件，分别记录 ESP32、Demo APP、SW APP 日志。
- 回归：BLE、OTA、BASE、PLUS、有激光、无激光、传感器异常和断电重启。
- 数据：空载点、多个载荷点、单调性、拟合误差、模型写入后重启保持一致。

## 11. 旧模型与缺少空载锚点的安全准备（2026-09-24）

本节是本日代码复核后的最新结论，优先于前文“E5 已关闭代码层缺口”的历史状态描述。它只冻结安全和持久化规则，不代表相关固件修正已经写入；本轮没有改固件或 APP 行为。

代码复核定位到两处必须修正的启动风险：

1. `LaserModule::loadCalibrationModel()` 当前把旧 `zero/factor` 键存在与否并入“已有持久化模型”判断。旧坐标的兼容值因此可能被当成活动校准，给体重计算和空载距离提供不可信基准。
2. `DistanceStateChain::update()` 当前在正式空载距离 `D_e` 不存在时，会把第一条有效距离临时当作空载参考。这样上电环境会影响有人/站稳状态，并可能让开始门禁提前就绪。
3. `SystemStateMachine::requestStart()` 已有 `runtime_ready`/`start_ready` 未满足时拒绝启动的路径；缺少校准锚点应保持这两个就绪值为假，返回现有 `NOT_ARMED`，不得伪装成传感器故障或进入无传感器降级启动。
4. 命令入口已核实：`WAVE:STOP` 只调用停止流程，不清除模型；`CAL:ZERO` 和当前仍存在的 `SCALE:ZERO` 都调用 `triggerZero()`，由测量任务执行清模。运行中清模保护尚未实现。

冻结的旧模型规则：

- 只有符合当前 `mdl_ver=1` 坐标定义、提交标记、CRC、有限值、0 kg 截距和单调性校验的主记录或备份记录可以继续使用；有效模型重启、断电和普通 OTA 后保持不变。
- 没有版本号的旧 `mdl_*` 记录，以及只有 `zero/factor` 的旧参数，不自动换算、不作为体重模型或 `D_e`，也不因启动而删除。第一次写入新格式前，先复制到独立归档、读回核对，防止同名键覆盖旧证据。
- 用户明确执行“参数归零”时清除活动模型、主备记录、兼容键和归档；上电、OTA、`WAVE:STOP` 均不得清除。运行中收到清模命令应拒绝且保持模型不变。

冻结的缺少 `D_e` 规则：传感器健康且当前距离有效时，继续向 Demo APP 输出真实距离；体重标无效；不采用首读数或实时读数代替 `D_e`；不输出正式的有人、站稳、离台或律动判断；保持 `runtime_ready=0`、`baseline_ready=0`、`start_ready=0`，开始/继续由现有门禁以 `NOT_ARMED` 拒绝。只有 Demo APP 从当前有效距离记录 0 kg 校准点、固件成功保存并重新确认当前格式模型后，才启用该模型的 `referenceDistance` 作为 `D_e`。

目前没有带传感器原始值、真实距离、0 kg 空载点和操作标签的 J100 数据，不妨碍先实现旧模型隔离、缺锚点封闭门禁及其自动化测试；但在补齐数据前，不冻结 `T_span_min_D`、空载/站稳阈值、距离版 16%/28% 映射或距离摔倒阈值，也不据代码现值宣称这些行为验收通过。详细规则见[施工蓝图第 13.28 节](./esp32_iic_preserve_all_function施工蓝图.md)。
